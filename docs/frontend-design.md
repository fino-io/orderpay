# Orderpay 前端设计文档

版本：v1.1 · 日期：2026-11-04 · 状态：已审查，待实现

## 1. 审查结论与范围

**订单作为工作入口、支付附属订单、管理员独立查审计的方向合理。首版收敛为四个业务页面，可作为受控本地环境的实施依据。** 正式业务开放依赖登录与部署验证；真实支付依赖渠道验收，不属于前端首版。

| 原方案问题 | 收敛决定 |
| --- | --- |
| 连接页、身份探测与业务查询重复；审计探测还会新增事件 | 连接设置放现有外壳，不单建连接路由，不调用接口探测身份 |
| 已关闭的支付能力仍设计了表单、开关和轮询 | 首版只展示支付信息，不实现申请入口、支付开关和轮询 |
| 游标深链接、页大小与自动刷新规则叠加 | 每页固定 20 条；筛选可分享，游标仅当前连接内使用；手动刷新 |
| CREATED 被描述成确定“待提交” | 改为“支付已受理”；是否可撤销由服务端事务判断 |
| 未知原因码和错误映射仍有歧义 | 异常组合不开放取消；只按实际可识别的业务码解释错误 |
| 首版与未来需求重复展开 | 首版保留明确页面、状态、接口和验收；后续只记录依赖 |

首版覆盖商户创建、查看、取消订单，以及管理员查询审计。复用现有导航、明暗主题、路由和生成客户端，不增加大屏、支付列表、退款、签约管理或人工核查处理台。

## 2. 现状与约束

当前工程使用 React 19、TypeScript、Vite、React Router，已有首页、API Console、Issues 和运行观察链接，尚无商户业务页面。现有主题和焦点样式可复用。

| 能力 | 已核对的事实 | 页面决策 |
| --- | --- | --- |
| 订单列表 | 只支持订单状态和游标，无总数 | 仅状态筛选，无总页数、数量徽标或全局搜索 |
| 排序 | 订单、审计均为 `(create_time ASC, id ASC)` | 标注“创建时间从早到晚”，不在当前页假排序 |
| 支付信息 | 列表只有 OrderView；详情聚合可空 PaymentView | 支付放详情，列表不逐行补查 |
| 商户隔离 | 身份来自凭证，跨商户资源返回不存在 | 商户不填写或切换 merchantId |
| 管理员权限 | 只能访问管理员接口，无跨商户订单查询 | 审计资源 ID 可复制，不链接商户订单详情 |
| 支付提交 | 正式装配未接真实授权适配器，当前返回 503 | 首版没有支付提交表单 |
| 审计查询 | 按 merchantId/resourceId 筛选；查询自身留审计 | 只在显式查询、翻页时请求 |
| 取消判断 | PaymentView 不含提交次数和首次提交时间 | 前端筛选候选，不保证一定能取消 |

正序和缺少商户订单号查找适合小规模验证，但会降低日常查单效率。正式运营前优先评估“最新优先”和“按商户订单号精确查找”，通过后端查询语义及契约落实；首版不以“最新订单”或“搜索全部订单”命名现有能力。

## 3. 页面与连接

| 路由 | 页面任务 | 主要操作 |
| --- | --- | --- |
| `/orders` | 找到订单 | 状态筛选、订单 ID 定位、翻页、进入创建 |
| `/orders/new` | 创建不可变订单 | 填写三个字段、提交 |
| `/orders/:orderId` | 查看订单与支付事实 | 刷新、取消候选订单 |
| `/admin/audit-events` | 定位审计事件 | 手动查询、翻页、展开详情 |

`/` 按所选工作模式进入订单或审计。主导航只显示“订单”或“审计事件”，右侧放主题与连接设置。现有 `/console`、`/issues` 保留，开发环境通过“开发工具”菜单访问；监控链接沿用现有目标。没有凭证时展示连接设置，不请求业务接口。

当前没有浏览器登录、当前用户或角色发现接口。受控本地使用只增加一个设置区：工作模式（商户/审计）、密码输入框和“应用连接”。API 地址沿用项目配置，不新增环境管理器。

- 工作模式只选择页面，不代表已验证的角色。应用连接不发送探测请求；商户进入列表时正常读取，审计页必须点“查询”。不为菜单、路由预加载或身份探测额外查询审计。
- 权限由真实业务请求校验；没有主体接口，不显示推测的商户名、merchantId 或“管理员已认证”。401 清除失效连接并提示重新配置；403 提示核对模式与凭证，不自动换角色。
- 凭证仅在内存，通过现有 `Authorization: Bearer` 协议传递；刷新页面后重新输入，不进入 URL、浏览器持久存储或 `VITE_*`。
- 应用新凭证、切换模式或清除连接时，取消读取请求、清空业务缓存和草稿，丢弃旧连接的迟到响应。每次连接创建内存作用域标识，不把凭证放进查询 key。
- 未保存草稿离开时提示；写请求在途时暂缓切换，并说明正在确认结果。中止浏览器请求不能撤销服务端业务。

正式开放时接入已有身份平台，由服务端管理服务凭证并提供浏览器会话，不自建账号密码系统。具体方式随部署确定，不将新增 BFF 作为首版独立工程。

## 4. 页面设计

### 4.1 订单列表

```text
Orderpay   订单                         主题  连接设置
────────────────────────────────────────────────────
订单                                      [创建订单]
[全部] [待支付] [已支付] [已取消]             [刷新]
按订单 ID 定位 [完整 UUID________________] [查看]

商户订单号 / 订单 ID     金额（CNY）  状态    创建时间  操作
SO-20261104-001          ¥19.90      待支付  …         查看
019… [复制]
────────────────────────────────────────────────────
创建时间从早到晚 · 每页 20 条          [上一页] [下一页]
```

状态切换调用 ListOrders：全部省略 status，其余按契约传 1/2/3，不在当前页过滤。ID 定位只接受完整订单 UUID，校验后进入详情，不冒充商户订单号搜索。

以商户订单号为主标识，订单 ID 为辅助信息并可复制；金额右对齐、两位小数。行内只保留“查看”，取消进入详情。描述和支付不放列表。

分页固定 pageSize=20，按 nextPageToken 前进；上一页只回看当前连接内已访问页。筛选存 URL，游标和页位置保留在内存，不设计游标分享或跨连接恢复。切换筛选、手动刷新、成功写入后回到当前筛选第一页；普通查看详情再返回保留列表位置。不展示总数或末页跳转，不自动抓取全部页。

首次无订单提供“创建订单”；筛选无结果提供“查看全部”。首次加载用表格骨架；刷新保留内容，失败显示旧数据标记和重试入口。

### 4.2 创建订单

独立页面，表单宽度约 640px，只填写三个字段：

| 字段 | 校验与说明 | 请求字段 |
| --- | --- | --- |
| 商户订单号 | 必填，最多 128 字符；使用业务系统的唯一订单号 | merchantOrderNo |
| 金额（CNY） | 以元输入，0.01～1,000,000.00，最多两位小数 | amountMinor，整数分，1～100000000 |
| 订单描述 | 必填，最多 200 字符；普通文本框 | description |

金额按十进制字符串转换为整数分，避免浮点乘法误差；拒绝负数、科学计数法、第三位小数和越界值。字符串长度与后端字符规则一致，拒绝纯空白；订单号和描述按用户确认内容提交，不在重试时改写。

底部显示确认金额和“创建后订单号、金额和描述不可修改”。按钮为“创建订单 / 创建中…”，无需额外确认框。成功跳转返回的订单详情；响应不能区分新建和幂等命中，反馈用“订单已确认”。

409 提示同订单号内容冲突，保留输入；不能根据商户订单号定位原订单，不提供推测跳转。超时或 5xx 显示“结果尚未确认”，保留提交快照，提供“重试原请求”；若用户要修改内容，明确提示先核对原单。不自动更换订单号或重试写请求。

未保存草稿离开时提示；提交中防重复点击；成功前不插入临时订单。

### 4.3 订单详情

```text
[返回订单] SO-20261104-001                    [刷新]
订单 ID 019… [复制]     最后获取时间 …（UTC+8）
────────────────────────────────────────────────────
订单状态  待支付                    金额 ¥19.90 CNY
[存在异常时，优先展示原因与下一步]
────────────────────────────────────────────────────
订单信息                        支付信息
商户订单号 / 描述                未创建支付记录
创建时间 / 更新时间              支付功能暂未开放
────────────────────────────────────────────────────
[取消订单]（仅在候选条件成立时可用）
```

宽屏两列、窄屏堆叠。支付存在时展示 PaymentView 的支付 ID、状态、金额快照、渠道引用、脱敏原因、创建和更新时间；无记录显示“未创建支付记录”。订单与支付状态分别展示，受理不等于支付成功。

渠道引用缺失显示“暂未取得”，不推断为未提交。不伪造提交/完成时间、历史时间线，不展示授权引用、卡号、渠道账户和调度字段。

取消候选规则统一见第 5 节。确认框展示订单号、金额和“取消后不能恢复，服务端会检查支付状态”，按钮为“保留订单 / 确认取消”。前端只改善交互，服务端事务最终裁决。

- 成功：用 CancelOrder 返回值更新订单，再读取完整详情同步支付；列表失效、重置分页。重读失败时保留已确认的取消结果，支付标记“待刷新”，不能显示成取消失败或支付已同步。
- 409：提示状态变化，刷新详情后重新判断动作。
- 超时/网络失败：提示结果未知，先查详情；查到已取消则确认结果，仍为候选时允许用户再次确认，不自动提交。
- 读取失败时禁用写操作；刷新失败保留旧数据并标记过期，成功读取后恢复。

### 4.4 管理员审计

筛选只有可选的商户 UUID、资源 UUID，以及“查询 / 重置”。初始提示“填写条件后查询”，允许不填条件显式查询全部。输入、展开、重新聚焦和重新挂载不触发请求；重置清空条件和结果，等待重新查询。

表格展示时间、操作、商户、资源、状态变化、操作者，每页 20 条。点击“详情”在行下展开其余字段，包括事件 ID、requestId、reasonCode、evidenceReference，不新增抽屉或详情路由。

每次查询和翻页自身留审计，明确提示列表不是固定快照。resourceId 精确匹配资源，查订单 ID 不自动包含支付 ID 对应事件。管理员不能打开商户详情；ID、证据引用仅提供复制，证据默认纯文本。不提供全量导出或不存在的时间、操作类型、请求 ID 筛选。

## 5. 状态与取消规则

| 对象 | 契约状态（省略枚举前缀） | 文案 |
| --- | --- | --- |
| 订单 | PENDING_PAYMENT / PAID / CANCELLED | 待支付 / 已支付 / 已取消 |
| 支付 | CREATED | 支付已受理 |
| 支付 | PENDING | 支付结果待确认 |
| 支付 | SUCCEEDED | 支付成功 |
| 支付 | DECLINED | 支付已关闭，未支付；结合原因解释拒付或撤销 |
| 任意对象 | UNSPECIFIED 或未知值 | 状态未知，请刷新或联系管理员 |

异常优先：RECONCILIATION_REQUIRED 为“结果需要核查”，CHANNEL_RESULT_CONFLICT 为“支付结果存在冲突”，COMPENSATION_REQUIRED 为“需要外部补偿处理”。ORDER_CANCELLED 为“订单取消，支付已关闭”，仅在已取消订单与 DECLINED 支付组合中解释为正常撤销；其他组合需核对。未知非空原因码显示脱敏码与核对提示，不当成正常。

先确认数据有效、订单支付关联及金额一致，并排除异常/未知原因，再按下表开放取消：

| 订单 / 支付组合 | 页面行为 |
| --- | --- |
| 待支付 / 无记录 | 可发起取消 |
| 待支付 / CREATED，原因码为空 | 可请求取消；仍可能已准备提交，服务端可以拒绝 |
| 待支付 / DECLINED，原因码为空 | 可发起取消；未来新增可接受的拒付原因时，必须有服务端明确码表依据 |
| 待支付 / PENDING | 禁用取消，提示支付结果待确认 |
| 已支付 / SUCCEEDED，无异常 | 展示已确认收款，不提供取消 |
| 已取消 / 无记录或 DECLINED，无异常 | 展示取消结果，不再提供取消 |
| 其他组合、未知状态或异常标记 | 提示核对，禁用取消，不用单一成功状态掩盖异常 |

等待超时不把 PENDING 改成失败。不提供“改为成功 / 核查完成 / 补偿完成”。订单 PAID、支付 SUCCEEDED 且无未关闭核查才满足架构中的可履约条件；页面只展示事实，不新增履约命令。

## 6. 接口与实现边界

前缀 `/orderpay/v1`，以下 payload 为传给生成客户端的参数：

| 场景 | RPC / HTTP | payload |
| --- | --- | --- |
| 列表 | ListOrders · GET `/orders` | `{ status?, pageSize: 20, pageToken? }` |
| 创建 | CreateOrder · POST `/orders` | `{ order: { merchantOrderNo, amountMinor, description } }` |
| 详情 | GetOrder · GET `/orders/{order_id}` | `{ orderId }` |
| 取消 | CancelOrder · POST `/orders/{order_id}:cancel` | `{ orderId }`，HTTP 无 body |
| 审计 | ListAuditEvents · GET `/admin/audit-events` | `{ merchantId?, resourceId?, pageSize: 20, pageToken? }` |
| 后续支付，不纳入首版 | CreatePayment · POST `/orders/{order_id}/payments` | `{ orderId, payment: { mandateReference } }` |

生成客户端会提取 order/payment，实际 HTTP body 为 OrderInput/PaymentInput。页面不重复写 fetch、URL 和序列化，不修改 generated、Console、Issues 等受管文件。

### 6.1 代码职责与依赖

- router.tsx、app-layout.tsx 负责路由、顶部导航及连接设置；订单页面、API 和展示转换放 app/orders/，审计放 app/admin/audit-events/。
- api/index.ts 复用生成传输，在一个边界解包成功结果、归一化错误。当前没有完整生成业务类型，只补最小契约类型，不复制内部领域模型。
- 沿用原方案的 TanStack Query 管理查询与失效，不自写缓存框架；这是待引入依赖，当前未安装。能力和默认行为见[官方概览](https://tanstack.com/query/latest/docs/framework/react/overview)、[默认配置](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)。首版关闭自动重试、聚焦/重连刷新与轮询，审计禁止挂载自动查询。
- 复用 React Router、CSS、主题；原生表格、普通表单、行内展开、dialog 与 Intl 足够。不引入全局状态库、图表库、通用 CRUD 或动态表单框架；实际复用后再提组件。

筛选使用 URL；页位置、游标、草稿和展开项在内存；服务端数据归查询缓存。查询 key 包含配置 API 地址、连接作用域、资源、筛选和分页参数，读取传递 AbortSignal。首次进入订单页读取，用户刷新时重取，返回列表可复用当前结果。“最后获取时间”指客户端读取时间，不冒充业务事件时间。

### 6.2 响应与错误

当前生成客户端在非 2xx 时只抛普通 Error。项目适配层通过 onResponseMeta/onResponseText 获取状态及公共错误，按实际部署 envelope 和业务码归一化，不按英文 message 猜测，不做未来协议兼容框架。

实施前用真实响应固定枚举、金额和 Fino Timestamp 解析；HTTP 200 也按配置检查业务错误。缺失金额、未知状态和转换失败不能默认为 0/待支付。当前金额上限低于 JavaScript 安全整数，验证为整数分后可用 number，ID 保持字符串。

| 错误 | 页面处理 |
| --- | --- |
| 400 | 可识别字段错误定位字段，否则显示通用说明；分页场景提供回第一页，不把所有 400 当游标错误 |
| 401 / 403 | 按连接规则处理，不自动换身份 |
| 404 | 订单不存在或当前连接无权访问，可返回列表 |
| 409 | 按创建/取消解释，保留输入或核对最新状态 |
| 429 | 提示稍后重试、保留内容；无后台自动刷新，无需冷却调度器 |
| 5xx / 断网 / 超时 | 读取可重试；写入按结果未知处理，不假成功 |

只有匹配 PaymentUnavailable 的实际业务码才解释为渠道未启用，通用 503 表示服务暂不可用。没有结构化字段或请求标识时不虚构定位信息。

## 7. 视觉与完整状态

沿用约 58px 顶栏、最大 1440px 内容宽度和语义颜色变量。正文约 14px、标题 22～24px，间距使用 8/12/16/24px；列表紧凑可读，以分隔线组织内容。金额右对齐、使用等宽数字，状态同时有文字和颜色。

业务样式限定自身区域，描述框避免继承 Console 的代码字体和 300px 高度。新增警示色覆盖明暗两种主题。

- 宽屏详情两列、窄屏堆叠，导航折叠。窄屏订单保留订单号、金额、状态、查看；审计宽表独立横向滚动，页面不横向溢出。
- 输入有常驻 label，错误可定位，表格有列头；键盘焦点可见。确认框支持 Escape、焦点约束与关闭后恢复；图标有可访问名称，触控目标约 44px，禁用原因可直接阅读。
- 覆盖初次加载、刷新、正常、首次为空、筛选为空、失败；保留输入与旧内容，并区分旧数据。成功使用状态区域，写入错误放动作附近。
- 时间按浏览器时区显示并标注时区，区分业务时间与最后获取时间；短时过渡尊重 reduced-motion。

## 8. 实施与验收

先核对响应、完成连接和请求边界，再实现列表/创建/详情及取消，最后补审计、明暗主题与窄屏。本阶段不修改业务 proto。

| 验收项 | 通过标准 |
| --- | --- |
| 查询分页 | 服务端筛选、20 条游标分页；切换条件/写入后回第一页；无假统计、假排序、支付 N+1 |
| 金额 | 0.01 元→1 分；1,000,000.00 元→100000000 分；拒绝负数、第三位小数、科学计数法和超限 |
| 幂等 | 同号同内容得到同一订单；异参 409 保留草稿；结果未知可重试原请求 |
| 取消 | 遵守候选矩阵，CREATED 的 409 正确处理；成功后重读失败不丢失已确认结果 |
| 连接隔离 | 商户 A/B、模式切换无旧缓存或迟到覆盖，无身份探测；密钥不持久化 |
| 审计副作用 | 仅查询/翻页发送请求；输入、展开、返回页面、聚焦均不触发 |
| 响应与失败 | 真实响应解析和错误可解释；不把超时、受理或通用 503 当支付终态 |
| 可用性 | 1440/768/390px、明暗主题、键盘下完成核心任务，无页面溢出 |

实施后运行 `cd frontend && npm run build`，针对金额转换、取消矩阵、响应适配和连接切换做关键行为验证。浏览器视觉与交互检查在实现后执行；本次文档审查不代表已经完成页面测试。

| 开放范围 | 前置条件 |
| --- | --- |
| 受控本地验证 | 现有服务凭证、开发 API 配置、订单及审计接口可用 |
| 正式业务开放 | 身份接入、服务端权限、API 转发/CORS、SPA 深链接验证；工具页按部署控制访问 |
| 真实支付开放 | 授权、渠道、回调、恢复与异常处理验收完成，再设计申请和跟踪，不提前实现开关或轮询 |

当前 Caddy 只代理 /monitor，未代理 /orderpay/v1；正式部署优先由现有同域网关转发业务 API，避免请求落到 index.html。开发沿用 config.ts/Vite 配置，不写死端口；隐藏菜单不替代访问控制。

后续优先评估最新优先与商户订单号精确查询。统计、完整事件链、跨商户订单查询、人工核查和导出，都需对应服务端能力后再设计，不列入首版待办。
